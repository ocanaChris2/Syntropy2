================================================================================
 RECURSIVE, BUDGET-DRIVEN, SELF-BENCHMARKING TRAINING
 (1) a concrete usage example for THIS repo, and
 (2) a portable prompt to replicate the strategy on ANY model / architecture.
================================================================================

This document covers the FULL strategy as it stands: the original 8 invariants
(recursive versioning, budget adaptation, fault-tolerant checkpointing, hard-gated
benchmarking, drift auto-fix, adaptive control, capacity escalation, stop+ledger)
PLUS three new invariants added after the original design:

  9.  Automatic model sizing from budget (FLOP-scaling ladder, no tier names)
  10. Multi-session continuity (unlimited sessions, cross-session state, architecture lock)
  11. Always-valid deployment artifact (live Rust export after every phase)

The 11 invariants are architecture-, framework- and status-agnostic.  The only
things that change between use-cases are the fill-in blocks in Part B.

 PART A — USAGE EXAMPLE  (Syntropy2 / neuro_symbolic_compressor.py)
--------------------------------------------------------------------------------

RECOMMENDED ENTRY POINT: run_budget()
  No tier names.  One number drives everything — model size, phase length,
  bench allocation — via a FLOP-calibrated ladder.  Works for 2 h or 200 h.

  # 0) Fast sanity checks (CPU, no downloads, ~1 min)
  python neuro_symbolic_compressor.py --smoke
  python neuro_symbolic_compressor.py --smoke-recursive

  # 1) Command-line (budget-only, recommended)
  python neuro_symbolic_compressor.py --budget-only --budget 80 --session-cap 25 --fresh-start
  #   --budget   = total hours across ALL sessions (sizes the model)
  #   --session-cap = wall-clock cap for THIS session (Kaggle hard-kills at 30 h)
  #   --fresh-start = ONLY on the very first session (wipes runs/)

  # 2) Python / notebook
  from neuro_symbolic_compressor import run_budget

  run_budget(total_budget_h=80, session_cap_h=25, fresh_start=True)   # session 1
  run_budget(total_budget_h=80, session_cap_h=25)                     # sessions 2, 3, ...

  # total_budget_h is locked into runs/accumulated.json on session 1 so the
  # model architecture stays consistent even if you change the number later.

  # 3) Full parameter reference
  run_budget(
      total_budget_h = 80,    # sizes the model; locked after session 1
      session_cap_h  = 25,    # wall-clock limit for THIS session
      outdir         = "/kaggle/working/runs",
      fresh_start    = False, # True ONLY for first session
      target_phases  = 4,     # training+bench slots per session
      seed           = 1234,
  )

LEGACY ENTRY POINT: run_recursive()  (tier-named, single-session)
  Still works.  Use when you want explicit tier control (nano/base/large):

  run_recursive(
      total_budget_h = 9,
      start_tier     = "nano",
      escalate_to    = "base",
      target_phases  = 4,
      session_cap_h  = 11.5,
  )

WHAT HAPPENS, PHASE BY PHASE:
  v001  cold start (or resume from previous session's last checkpoint)
        -> train time-slice -> export to runs/current/ -> benchmark
        -> calibrate -> record in ledger
  v002  resume v001 (model + optimizer + LR scheduler + RNG + counters)
        -> train more -> export -> benchmark -> COMPARE to v001
        -> fix drift -> if better: also copy to runs/best/
  vNNN  ...repeat indefinitely across sessions...

WHAT YOU GET (under runs/):
  runs/current/             ONNX models + config.json + tokenizer.json +
                            calibration.json — updated after EVERY phase,
                            even if the session was killed before benchmarking.
                            Always a valid, loadable Rust artifact.
  runs/best/                Same files, only updated when a new bpb record is set
                            AND the lossless round-trip passes.
  runs/ledger.json          Append-only phase history (step, bpb, calibrated bpb,
                            gzip/xz, lossless gate, calib_T, verdict, delta, is_best).
                            Shared and extended across ALL sessions.
  runs/accumulated.json     Cross-session state: elapsed_h, total_budget_h
                            (architecture lock), n_phases.
  runs/v{N}/best.pt         Portable best checkpoint (model + cfg + step + val_bpb;
                            weights_only-safe).
  runs/v{N}/best.pt.last    Full resume state (model + optimizer + scaler + RNG +
                            step + best + patience + cfg).
  runs/v{N}/hourly_{N}.last Latest hourly safety checkpoint (same format as .last).
  runs/v{N}/latest_hourly.json  Pointer: {"path": ..., "step": N}
  runs/v{N}/benchmark.json  Per-phase benchmark metrics.
  runs/cache/               Cached BPE + classical features (reused across sessions).

MULTI-SESSION WORKFLOW (80 h total / 25 h Kaggle sessions):
  Session 1   FRESH_START=True,  total=80, cap=25
              -> d=384 (23 M params) chosen from FLOP ladder
              -> trains ~22 h (4 phases × ~5.5 h)
              -> benchmarks ~2 h
              -> writes accumulated.json: {elapsed_h: ~24.5, total_budget_h: 80}

  Session 2   FRESH_START=False, total=80, cap=25
              -> reads accumulated.json: locked to 80 h, resumed at ~24.5 h
              -> reads ledger.json: resume_from = v004/best.pt.last
              -> continues training from step N+1, same architecture
              -> exports to current/ after every phase

  Sessions 3+ Same — truly unlimited.  Pass the same total_budget_h so the
              architecture warning is not triggered.

UNEXPECTED KILL RECOVERY:
  If Kaggle kills the process mid-phase (ledger was last written at v003):
  - Session restarts, reads ledger: resume_from = v003/best.pt.last (step 9100)
  - Scans v*/latest_hourly.json: finds v004/hourly_01.last (step 11420)
  - 11420 > 9100 -> uses v004/hourly_01.last as resume_from
  - Continues from where it was actually killed, not from the last committed phase

capability to my codebase WITHOUT changing the model's math or breaking existing
entry points.  The capability turns a compute budget into a chain of resumable,
benchmarked "versions" that get progressively and verifiably better, always keeps
the best, always produces a valid deployment artifact, and can be interrupted and
continued across an unlimited number of sessions.

REQUIRED STRATEGY — implement ALL 11 of these invariants (architecture-agnostic):

1. BUDGET IS MANDATORY AND AUTO-ADAPTIVE.
   - No hardcoded budget anywhere.  Resolve by strict precedence:
       explicit argument > module-level config variable > interactive prompt > hard error.
   - Derive EVERYTHING ELSE as fractions of the resolved budget B: phase length
     (= min(per-session cap, B / target_phases)), escalation threshold (only escalate
     if a configurable fraction of B remains), bench/test allocation, and the
     "remaining = B_total - accumulated" cross-session math.
   - The identical code must behave sensibly for a tiny budget and a huge one.

2. PHASE-BASED, FAULT-TOLERANT, FULL-STATE CHECKPOINTING.
   - A "phase" is one time-/step-sliced unit of training bounded by the phase budget.
   - Persist FULL state to resume EXACTLY: weights + optimizer + LR scheduler +
     RNG/seed state + step/epoch counters + best-so-far + early-stop counters.
   - Write atomically (temp file + rename) so a kill mid-write never corrupts a file.
   - Keep TWO artifacts per phase: a PORTABLE "best" checkpoint (weights_only-safe,
     safe to load/share, weights + minimal metadata) and a LATEST "resume" checkpoint
     (full internal state).  The portable one must keep existing loaders working.
   - Additionally, write an HOURLY SAFETY CHECKPOINT inside the training loop:
     every 1 h wall-clock, save the full resume state to a timestamped file
     (e.g. hourly_01.last) and write a pointer file (latest_hourly.json: {path, step}).
     Keep only the latest hourly on disk to bound storage.  This decouples crash
     safety from the step-based periodic save and survives unexpected kills.

3. RECURSIVE VERSIONING.
   - Each new VERSION resumes the previous version's latest full state and continues
     the GLOBAL training schedule (don't restart the LR schedule or step counter).
   - After training, benchmark the version, COMPARE it to the DIRECT previous version,
     and maintain a "best across all versions" that is only ever updated by a version
     that passes the hard gate.  Never ship something worse than the best so far.
   - Version numbering is GLOBAL across sessions: v003 in session 2 is not a reset.

4. PROFESSIONAL BENCHMARK with a HARD GATE.
   - Report the primary metric on held-out (and "real"/stress) data vs the baselines.
   - Enforce the hard correctness/quality gate as a boolean that GATES selection.
   - Also report a cheap throughput / cost number, honestly labeled.
   - Prefer reusing the codebase's existing eval/verification utilities over new ones.

5. QUALITY-DRIFT DETECTION + AUTO-FIX (generalize "calibration").
   - Measure a domain-appropriate drift signal between versions (for probabilistic
     models: optimal temperature deviating from 1, or ECE worsening; for others: an
     analogous monotonic post-hoc correction or guard).
   - If drift is detected, apply the cheap monotonic fix (e.g. temperature scaling) and
     record/bake it into the exported artifact.  A fix must never worsen the val metric.

6. ADAPTIVE CONTROL FROM THE PRIOR BENCHMARK.
   - Use the previous version's verdict to set the next version's knobs: e.g. lower the
     learning rate on regression or detected drift, lower it less on plateau, keep it on
     clean improvement.  Keep this policy small, explicit and logged.

7. OPTIONAL CAPACITY ESCALATION (only if provided).
   - When the current capacity plateaus AND enough budget remains, promote to the larger
     config.  Be HONEST about weight transfer: if dimensions/vocab differ you cannot copy
     weights — start the larger model fresh, rely on "keep best" so escalation can never
     regress the deliverable.  If budget is too small to help, keep refining instead.

8. STOP CRITERIA + LEDGER.
   - Stop the current SESSION at the per-session cap.  Resume in the next session.
     The global training schedule stops at: target metric met, plateau (< eps improvement
     between versions), or a deliberate decision to stop adding sessions.
   - Never prevent a new session from starting based on accumulated hours alone.
   - Maintain an append-only ledger (json + human-readable table) extended across ALL
     sessions, with one row per version: step, metric, calibrated metric, baselines,
     gate pass/fail, drift-fix, verdict, delta, and a marker on the best.

9. AUTOMATIC MODEL SIZING FROM BUDGET (NO TIER NAMES).
   - Build a sizing ladder: a list of (architecture, recommended_steps) entries ordered
     smallest to largest, each calibrated from a known FLOP-throughput reference point
     (e.g. steps/hour on a T4 for the base config, scaled linearly by parameter count).
   - config_from_budget(train_h): iterate the ladder and select the LARGEST config
     where at least a minimum fill fraction (e.g. 25%) of its recommended steps are
     achievable in the available training hours.
   - The budget is split first: bench_h = clamp(total * bench_frac, min, cap);
     train_h = total - bench_h.  Subtract an estimated prep time before sizing.
   - If actual prep time exceeds the estimate significantly (first session only), re-derive
     the config and rebuild data structures only if vocabulary changed.
   - This replaces all hardcoded tier names in the user-facing API.  The only input is hours.

10. MULTI-SESSION CONTINUITY (UNLIMITED SESSIONS).
    - total_budget_h serves ONLY as the model-sizing input (invariant 9).  It is NOT
      a hard limit on how many sessions can run.  Sessions are unlimited.
    - On the first session, lock total_budget_h into a cross-session state file
      (accumulated.json: {elapsed_h, total_budget_h, n_phases}).  Subsequent sessions
      read it from there.  If the caller passes a different value, warn and keep the
      locked value — model weights are incompatible across architectures.
    - Cross-session resume: at session startup, load the ledger and set
      resume_from = ledger[-1]["last_path"] (last completed phase).  Then scan ALL
      v*/latest_hourly.json files; if any has a step count higher than the ledger's
      last entry AND the file exists on disk, use it instead (crash recovery from
      an interrupted phase whose ledger row was never written).
    - The per-session cap (session_cap_h) is always respected as an independent limit.
    - Accumulated hours are tracked for information and logged, but never block a session.

11. ALWAYS-VALID DEPLOYMENT ARTIFACT.
    - Maintain a "current" output directory (e.g. runs/current/) that is updated after
      EVERY training phase, before benchmarking, using a temporary calibration_T=1.0.
    - After benchmarking, refresh it with the calibrated temperature.
    - Separately maintain a "best" output directory updated only on a new quality record.
    - Both directories must always contain a complete, self-contained artifact that the
      downstream consumer (Rust runtime, ONNX inference, REST API, etc.) can load
      without any additional post-processing.  A 4-hour interrupted session must still
      produce a usable runs/current/.
    - Write the artifact atomically (export to a temp subdir, then rename) to avoid
      serving a half-written state to a concurrent reader.

HANDLE "CURRENT MODEL STATUS" EXPLICITLY:
  - from scratch ................ session 1 phase 1 starts cold.
  - resume existing checkpoint .. session 1 loads <path> as starting full state.
  - pretrained init ............. session 1 initializes weights from <id/path>, fresh opt.
  - continue a run in progress .. detect the latest persisted resume checkpoint (ledger +
                                  hourly scan, invariant 10) and extend the global
                                  schedule from it — no resets to LR or step counter.

ENGINEERING REQUIREMENTS:
  - Deterministic: save and restore all RNG state; same budget + seed => same trajectory.
  - Cache expensive, deterministic preprocessing to disk; reused across sessions.
  - Idempotent and crash-safe; no silent defaults; fail loudly on missing budget.
  - Match the existing code's style and reuse its functions; minimal, surgical edits.
  - Single new entry point, e.g. run_budget(total_budget_h, session_cap_h, ...).
  - Keep the previous entry point (run_recursive / run_full) working unchanged.

DELIVERABLE SELF-TEST (must add and must pass, fast, on CPU):
  Add a tiny self-test that asserts, on a tiny/synthetic instance of the model:
    (a) resume restores step/optimizer/best EXACTLY (checkpoint round-trip);
    (b) benchmark dict has all keys AND the hard gate passes on a known-good case;
    (c) ledger has >=2 rows with monotonic best-tracking after two versions;
    (d) drift-fix does not worsen the val metric;
    (e) budget resolver returns the arg, then the variable, then raises without either;
    (f) cached preprocessing is reused (cache hit) on the second version;
    (g) hourly checkpoint is written after simulated 1h elapsed, pointer file exists;
    (h) runs/current/ is populated after a phase even if benchmark was skipped;
    (i) accumulated.json is written with locked total_budget_h after session ends;
    (j) a session starting with FRESH_START=False picks up resume_from from ledger
        OR from an hourly checkpoint if its step is more recent.
  Also keep any existing smoke/regression test green.

VERIFY by running the self-test and the existing smoke test, and show me the output.
Do not claim success without running them.

Example instantiation for a DIFFERENT model (an image classifier), showing how the
same 11-invariant strategy maps onto a totally different architecture:

  - Framework ................. PyTorch
  - Architecture .............. ResNet-50 → ResNet-101 image classifier
  - Current model status ...... initialize from a pretrained ImageNet checkpoint
  - Training entry point ...... train.py:fit()
  - Primary quality metric .... top-1 val accuracy (higher is better)
  - Baselines ................. previous best checkpoint; a linear-probe baseline
  - HARD gate ................. no NaNs in logits AND val accuracy >= last shipped model
  - Eval data ................. val split + a corrupted/"stress" split (blur, noise)
  - "Acceptable" .............. best within budget, stop if <0.2% gain between versions
  - Budget unit ............... GPU-hours (total=80h, per-session cap=8h on cloud)
  - Capacity escalation ....... ResNet-50 -> ResNet-101 on plateau with >=30% budget left
  - Deployment artifact ....... TorchScript + config.json + preprocessing stats

How the 11 invariants map here:
  - #1  budget ................ 80 GPU-hours total; 8h/session; phases = min(8, 80/10) = 8h
  - #2  checkpointing ......... best.pt (weights only) + best.pt.last (full) + hourly_N.last
  - #3  versioning ............ R50 v001→v002→... resume optimizer+scheduler+step always
  - #4  benchmark ............. top-1 on val + stress splits vs linear-probe baseline
  - #5  drift ................. temperature scaling + ECE; baked into TorchScript export
  - #6  adaptive control ...... lower LR factor on regression; keep on improvement
  - #7  escalation ............. R50→R101 on plateau; cannot copy weights → fresh R101,
                                 keep best so escalation can never regress deliverable
  - #8  stop+ledger ........... per-session 8h cap; global stop on plateau; append ledger
  - #9  auto-sizing ........... sizing ladder: R18/R34/R50/R101/R152 mapped to GPU-h;
                                config_from_budget(train_h) picks largest feasible
  - #10 multi-session ......... total=80 locked in accumulated.json; sessions unlimited;
                                hourly scan on startup recovers from cloud pre-emption
  - #11 artifact .............. runs/current/ has TorchScript + config after every phase;
                                even a 2h pre-empted session gives a loadable model

Other quick mappings (metric / hard gate / drift signal):
  - LLM fine-tune ....... eval loss or pass@k / output-schema or safety-filter validity / temperature scaling
  - Diffusion ........... FID or CLIP score / generated-sample validity / variance of calibration
  - RL policy ........... mean eval return / completes N eval episodes without crash / policy entropy guard
  - Tabular GBM ......... AUC or logloss / monotonicity & calibration constraints / isotonic recalibration
  - Compressor (this) ... bits-per-byte vs gzip/xz / lossless encode->decode round-trip / temperature scaling
